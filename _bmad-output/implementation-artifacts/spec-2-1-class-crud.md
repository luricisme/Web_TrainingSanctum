## Intent

**Problem:** `/classes` is a placeholder and no Class, Folder or Card tables exist, so a user cannot organise study material (FR-5, first half).

**Approach:** Add the Class, Folder, Card and SchedulingRecord tables, `/api/classes` Route Handlers (list, create, rename, delete with move or delete-all, both atomic), and a Classes page with an empty state, list rows and the rename and delete modals.

## Boundaries & Constraints

**Always:**
- Every Class belongs to a `userId`; every handler calls `requireSession`, validates with Zod (AD-6), returns the AD-10 envelopes, and scopes all queries to the session user. Another user's Class id returns `404`.
- Creating a Class creates its single `isUnsorted` Folder in one `$transaction`. A partial unique index on `(classId) WHERE isUnsorted` enforces one Unsorted Folder per Class (raw SQL in the migration).
- Both delete modes run in one `$transaction` (AD-11) and log one structured line (operation, counts, outcome).
- Move mode: Unsorted Cards merge into the target's Unsorted Folder; other Folders move with their Cards; a name already used in the target gets " (2)", then " (3)" and so on. Target must be another Class of the same user.
- Delete-all requires the request to carry the exact Class name (server-checked), mirroring the typed-name gate.
- Model names are `Class`, `Folder`, `Card`, `SchedulingRecord`; if Prisma rejects `Class`, use `StudyClass` with `@@map("classes")`, keeping "Class" in UI and API paths.
- Domain logic that is pure (name validation, " (n)" suffixing) lives in `packages/domain`; only `app/api/**` imports it, except Zod schemas the UI may import (AD-1).
- UI uses DESIGN.md tokens via `globals.css`, the Design DNA `design_style`, and the anti-generic rules; the accent marks the one primary action per screen.

**Never:**
- No Folder CRUD UI, no Class detail page (Story 2.2), no Card creation or editing (Stories 2.3 to 2.5), no code writing `SchedulingRecord` rows.
- No Server Actions; no raw SQL outside the migration; no new dependencies (TanStack Query is already installed).
- Class rows do not link anywhere yet.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Empty list | User has no Classes | Empty state: "Create a class to start adding cards." and primary "Create class" | N/A |
| Create | `POST {name:"IELTS"}` | `201`, Class plus one "Unsorted" Folder, row appears at once with "1 folder · 0 cards" | Name blank or over 80 chars after trim: `400` with `fields.name` |
| Rename | `PATCH {name}` on own Class | `200`, new name shown in the list and the delete modal | Unknown or foreign id: `404` |
| Delete, move | Class with Folders, other Class exists, `{mode:"move",targetClassId}` | Folders and Cards moved, name clashes suffixed, Class removed | Target missing, foreign or equal to source: `400`; any failure rolls back everything |
| Delete, all | `{mode:"delete",confirmName}` equals the Class name | Class, Folders, Cards, SchedulingRecords removed | Name mismatch: `400`, nothing deleted |
| Only Class | No other Class exists | Modal offers only "Delete class and everything in it" | `mode:"move"` returns `400` |
| Unauthenticated | No session | `401` envelope | N/A |

- **medium, patch** — Clicking the dialog's own padding closes it (Edge): `onMouseDown` tests `event.target === dialog`, and the padding belongs to the dialog element, so a stray click loses a typed confirmation name.

## Design Notes

Card and SchedulingRecord tables are added now, schema only, because Class rows and the delete modal show card counts and the cascade and merge rules need real rows to be testable; Story 2.3 owns the code that writes them. Duplicate Class names are allowed (the merge already copes with Folder name clashes, and the typed-name gate still works). Moving Folders is an `updateMany` on `classId`; merge is `updateMany` on the Unsorted Cards' `folderId` before deleting the source Class.
